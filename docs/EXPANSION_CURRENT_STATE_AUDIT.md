# WARSEED 当前游戏状态与扩充就绪度审计

> 审计日期：2026-08-19
> 审计对象：当前工作区（包含未提交实现），不是远端 `main` 的静态快照
> 验证方式：代码/Resource/场景/文档交叉检查、现有截图检查、当时 13 套 headless 测试与四关 smoke 实跑
> 状态说明：本文保留 2026-08-19 审计快照；D-026 已取消真人证据硬门，D-027 已启用 [`GAMEPLAY_REWORK_ROADMAP.md`](GAMEPLAY_REWORK_ROADMAP.md)，实时状态以 [`AI_DEVELOPMENT_STATE.md`](AI_DEVELOPMENT_STATE.md) 为准。

## 1. 执行结论

当前项目已经完成一个工程质量较高、产品方向明确的四关 MVP 候选切片。最有价值的资产不是某一张地图或某组数值，而是以下可复用边界：

```text
Input / UI / Agent
        -> GameCommand
        -> CommandValidator
        -> CommandQueue
        -> SimulationWorld（10 Hz 权威状态）
        -> WorldSnapshot / SimulationEvent
        -> Presentation / HUD / Audio
```

这条链已经支持战前军团编成、将领 Agent、整卡接管/归还、路线与阵线、补给、资源区、支援、地形、情报、敌方锁定计划、组织度、撤出和跨局成长。后续开发应保留该链，并把内容特判从 `SimulationWorld` 中逐步移到类型化系统与数据定义。

项目目前适合进入“验证后扩充”，但不适合立刻批量制作十几张地图。先决条件有两个：

1. 完成 P6.7 陌生玩家验收，证明核心交互不是只有开发者能理解；
2. 先补目标、地图、单位编制和战役数据模型，避免每个新增关卡继续增加硬编码分支。

## 3. 当前可玩闭环

当前主流程已经完整连接：

```text
作战区选择行动
  -> tick 0 战前编成
  -> 将部队卡分配给将领
  -> 选择战法、姿态、首发和预备
  -> 实时会战
  -> 将领意图 / 整卡路线和阵线 / 支援
  -> 总部摧毁或超时
  -> 战后现员、战损、补员、荣誉、装备
  -> 返回作战区进入下一行动
```

四关共享同一份稳定卡牌 ID 军团记录。当前存档格式为 v3，保存：

- 每张卡的授权兵力、现员、本局损失、累计损失和参战次数；
- 一项荣誉和一项装备；
- 组织度、最近状态和最近场景；
- 全局补充点、功勋、战役日与战斗次数。

胜利固定奖励 12 补充点/3 功勋，失败固定奖励 8 补充点/1 功勋。补充一个实体基础消耗 2 补充点并推进 1 战役日，成长可额外改变补充成本与整备日。

## 4. 当前内容盘点

### 4.1 四场正式会战

| 行动 | 地图与时限 | 玩家内容 | 敌军初始编队 | 独立机制 |
|---|---|---|---|---|
| 灰脊矿区 | 6144x4096，4800 tick（8:00） | 3 将领、4 卡、2 首发、人口 40 | 12 突击 + 2 先遣 | 三区资源、基础情报、三套锁定计划 |
| 断桥回声 | 6144x4096，5400 tick（9:00） | 3 将领、6 卡、3 首发、人口 52 | 14 突击 + 4 侦察 | 主桥瓶颈、工程渡口、高地收益 |
| 雾林输线 | 6144x4096，5600 tick（9:20） | 3 将领、6 卡、3 首发、人口 52 | 12 突击 + 6 侦察 + 5 屏护 | 情报淡出/过期、运输护送、补给节点、合法拦截 |
| 黑井反击 | 7168x4608，5200 tick（8:40） | 5 将领、12 卡、6 首发、人口 100 | 18 突击 + 8 侦察 + 8 火力 + 10 预备 | 组织度、多轴增援、有限撤出、六类支援 |

每场均有 3 套开局前锁定的敌方计划和 4 条反应规则。计划选择发生在读取玩家本局命令之前，反应读取敌方阵营合法知识，符合产品公平性原则。

### 4.2 经济现状

会战模式使用单一战中资源“补给”：

- 灰脊/断桥/黑井每 20 秒基础 +1，雾林每 22 秒 +1；
- 战略区每 30 秒结算，通常产出 +1 或 +2；
- 资源区有控制与争夺状态，但没有独立占领进度；
- 侦察、筑垒、补员、工程、火力、机动和后勤支援消耗 2—3 补给；
- 预备部队部署消耗 2—4 补给并等待 7—11 秒；
- 雾林运输纵队激活节点后提高补给上限、即时补给和区域收入；
- 补给达到上限后溢出直接丢失，没有仓储、线路或预留队列。

该经济足以制造预备队与支援的机会成本，优点是认知负担低；缺点是“占点后定时加数字”的变化有限，无法表达补给线被切断、孤军深入、运输损耗或不同任务类型的经济压力。

### 4.3 单位与部队卡现状

单位目录共有 6 种底层单位定义：

| 单位 | 会战用途 | 关键数值/能力 |
|---|---|---|
| 侦察车 | 侦察卡 | 速度 180，生命 120，视野/射程较高 |
| 突击车 | 突击与装甲卡 | 速度 160，生命 180，护甲 10，近中程火力 |
| 导弹车 | 火力与防空名义卡 | 速度 135，生命 130，射程 420，高单发低射速 |
| 工程车 | 工程/整补卡 | 无主动攻击，可施工和维修 |
| 运输车 | 后勤卡 | 无攻击、无反击，视野 176 |
| 矿车 | 旧基地 RTS | 采矿与有限自卫，不属于会战核心编成 |

当前 12 张部队卡主要通过名称、角色、授权兵力、部署成本/时间和所属将领产生差异。底层映射为：

- 侦察：游隼、开路侦察，共用侦察车；
- 突击/装甲：铁壁、装甲矛头、黑井警卫、机动反击，共用突击车；
- 火力/防空：雷鸣、高地火力、防空火力，共用导弹车；
- 工程：桥梁工程、战场整补，共用工程车；
- 后勤：前线运输，共用运输车。

因此当前“12 张卡”的组织差异明显大于战术实体差异。尤其“防空火力分队”没有独立防空目标类别或拦截行为，“装甲矛头”也没有与突击群不同的装甲/武器定义。

### 4.4 卡牌与成长现状

当前已存在：

- 5 名将领；
- 12 张部队卡；
- 12 张战法卡；
- 12 项荣誉/装备成长；
- 7 种跨关卡支援行为（单关最多 6 种）。

战法确实改变 Agent 行为，不是纯说明文字，但实现主要依赖 `SimulationWorld` 中按 doctrine ID 分支。`DoctrineDefinition` 本身只有名称、行为说明和代价说明，没有类型化效果列表或参数。

成长具备攻击、护甲、速度、视野、射程、组织恢复、部署补给和补充成本修正。每张卡只有一个荣誉槽和一个装备槽，装备后当前没有拆卸、替换、损坏或兼容标签规则。

### 4.5 地图现状

四个场景都是同一 `game_root.tscn` 的轻量实例，只切换 `scenario_kind`。战场表现由 `battlefield.gd` 程序化绘制，地图场景中的 `TileMapLayer` 尚未承担正式地形资产。

导航事实：

- 逻辑格固定为 32 世界单位；
- `MapDefinition` 仍只有一份 `test_arena.tres`；
- `LogicGrid` 硬编码预加载该测试地图；
- 会战可通过 `battlefield_bounds` 改变网格尺寸；
- 有 `navigation_blocked_rects` 的关卡使用矩形数据生成阻挡；
- 未提供独立阻挡数据时会回落到 `create_test_map()` 的程序化测试障碍；
- 地形效果主要由最近战略区的 `terrain_key` 推导，而不是来自完整地形区覆盖。

这意味着当前地图“在规则上可区分”，但尚不是可由关卡设计师稳定生产的正式地图管线。

### 4.6 胜负与任务现状

会战层的权威胜负只有两条：

- 最后一座敌方指挥中心被摧毁，对手失败；
- 到达会战时限时，玩家失败、敌方胜利。

同一 `_update_victory()` 也服务旧基地 RTS。雾林的护送节点、断桥的工程路线、黑井的撤出和组织度均影响战斗过程或跨局保存，但不会独立结束会战，也没有主要/次要目标等级。

旧基地 RTS 仍有一个 `MissionState`，要求发展、防守、攻击、接管导弹单位并归队，但它是旧技术切片任务记录，不是当前四关的胜利框架。

## 6. 关键设计债务

### 6.1 `BattleDefinition` 责任过多

当前单个 Resource 同时保存选择页元数据、地图尺寸、经济、总部、编成、情报、敌军计划、工程、护送、撤出和组织度。继续添加天气、胜利条件、补给线和剧情会显著增加交叉校验与场景特判。

建议拆为：

```text
BattleDefinition
 ├─ BattleMapDefinition
 ├─ BattleRosterDefinition
 ├─ BattleEconomyDefinition
 ├─ BattleObjectiveSetDefinition
 ├─ BattleIntelPackageDefinition
 ├─ BattleEnemyPlanSetDefinition
 └─ BattleNarrativeDefinition
```

### 6.2 `SimulationWorld` 承担过多场景规则

单位部署、所有支援、战略区、护送、拦截、组织度、撤出、战法特判和胜负均集中在同一大类。当前仍可测试，但扩展到 12 场行动后会使任何修改都影响所有关卡。

建议按权威系统拆出目标、补给网络、组织度和战法效果执行器；`SimulationWorld` 只负责顺序、状态所有权和系统协调。

### 6.3 卡牌数据不能表达混成编制

`UnitCardDefinition.unit_definition_id` 只有一个引用。真实军团卡应能表达主战、侦察、工程、雷达或防空条目的稳定组成，并分别承受战损。新增混成能力必须先解决稳定条目 ID 和存档迁移，不能只在生成时临时拼接单位。

### 6.4 地形与战略区耦合

目前最近战略区近似决定单位所在的地形。这对三个大色块的灰盒足够，但无法处理道路穿越林地、桥面覆盖河谷、建筑内部、反斜面或小范围高地。地形区、目标区和经济区必须成为不同数据对象。

### 6.5 胜负结果过于二元

当前失败仍会固定获得补充点和功勋，且跨关自测四战全部失败也能完成流程。这证明失败恢复有效，却不能形成“完成任务但损失惨重”“保存残部后有序撤离”“次要目标失败”等战役叙事。

需要把“战场结束条件”“胜负等级”“战役后果”分开计算。

## 7. 文档一致性问题

现有文档跨越多个快速开发阶段，部分状态描述已过时：

- 较早审计仍要求保持四张部队卡，而当前已经有十二张；
- 部分限制文字仍称成长只有一项荣誉和一项装备，当前实际是十二项定义、每卡各一个槽；
- 个别 MVP 状态文字称 120 实体低于 16.667 ms，而最新性能基线为 19.931 ms，明确未通过 60 FPS P95；
- “72/72 平衡审计通过”容易被误读为 72 场完整对局。实际主动策略主要采样 200 tick，只有故意失败案例加速到时限；它验证命令合法、早期差异和确定性，不验证完整胜率；
- GDD 中“场景特定目标”属于设计目标，当前代码仍只有总部摧毁和超时。

本审计在“当前事实”上优先于上述历史状态文字，但不覆盖既有产品原则。

## 8. 扩充前的放行条件

### 8.1 可以立即进行

- P6.7 真人试玩与问题闭环；
- 文档、数据校验、内容报表和可视化诊断；
- 不改变玩法的代码拆分测试；
- 通用目标系统的纯模拟原型；
- 一种新底层单位行为的纵向验证；
- 地图数据格式与导入/验证工具原型。

### 8.2 暂不建议立即进行

- 一次制作 8 张以上新地图；
- 把正式实体目标直接提高到 120；
- 增加第二种可消费战中货币；
- 增加随机掉卡、稀有度、抽取或牌库构筑；
- 为每张新战法继续在 `SimulationWorld` 添加字符串 ID 分支；
- 在没有目标框架时用场景脚本制作护送、坚守或撤离胜利；
- 在地图仍为程序化灰盒时投入大批最终美术。

## 9. 推荐的第一扩充切片

第一扩充切片应只增加一场新行动，但必须同时验证四项新能力：

1. 一种非总部摧毁主目标，例如“确认两个目标并撤离”；
2. 两种真正的新底层单位，例如无人侦察机和电子战车；
3. 一张使用独立地图定义、地形区和部署区的正式灰盒地图；
4. 一个战役节点结果，能根据胜负等级改变下一行动的情报或支援预算。

该切片成功后再批量扩充内容，可以最大限度复用同一数据与测试管线。
