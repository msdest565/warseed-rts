## 稳定身份与兼容

正式控制粒度始终为整张部队卡。`UnitCardCompositionEntry` 使用永久 `entry_id`，以及兵种、授权数量、编队角色和补员优先级。编译后的条目按 ID 稳定排序；补员按优先级升序、ID 升序填补缺口。换序不能交换损失记录或改变成员兵种。

旧资源的空 composition 由一个集中兼容编译入口生成 `main`，保持原 `unit_definition_id`、`authorized_strength` 和角色；不修改共享 Resource。新混成定义必须能在加载时校验空项、重复 ID、引用、数量、总编制和受支持角色。首个 fixture 只用现有兵种，不启用 D-022 的新战斗维度。

每条目保存可用人数和稳定成员归属，快照另计算当前存活人数。阵亡实体从世界清理后，不依靠已不存在的 UnitState 重建条目身份。撤离前记录各条目幸存人数；关卡结束与下一关恢复均按条目汇总，不能把一个兵种的损失补成另一个兵种。荣誉、装备与组织仍是整卡状态。

必须接通开局创建、预备部署、战地补员、整卡控制、撤离、战损写回、编成补充和跨关恢复。已有工程动作是否可用，要核对该卡当前实际存活的工程成员；UI、决策投影、将领选择和命令校验必须一致。

## v4 持久化形状

继续使用既有 `format_version` 表达文件结构，新增独立内容版本和迁移来源。composition 使用 ID 作键，不用数组下标。例如 v3 中铁壁的 12/9 兵力迁入以下结构，其余卡牌及战役字段原值保留：

```json
{
  "format_version": 4,
  "content_version": 1,
  "migrated_from_version": 3,
  "cards": {
    "ironwall_assault_group": {
      "authorized_strength": 12,
      "available_strength": 9,
      "composition": {
        "main": {
          "unit_definition_id": "assault_vehicle",
          "authorized_strength": 12,
          "available_strength": 9
        }
      }
    }
  }
}
```

上例只展示变化字段，不是完整存档。迁移保留荣誉、装备、组织、累计损失、最近损失、幸存场次、补充点、功勋、战役日、战役计数及结果。v1/v2 沿用原来缺省字段初始化规则，再进入相同 main 迁移。v3 不含兵种的记录从对应稳定卡牌的旧兼容定义解析；未知或已经不兼容的定义须明确报错，不能猜测新的混成比例。

v4 条目总授权、总可用和整卡汇总必须相等；人数是有限非负整数，可用数不能超过授权数。字段类型错误、未来格式/内容版本、未知条目或不匹配兵种不能经强制类型转换静默纠正。四关共用军团记录，当前关卡未出现的卡牌仍原样保留；本项不删除内容，也不删除历史记录。

## 写入与失败

加载结果必须区分缺档、成功、已迁移和失败，并携带源版本、字段原因和备份位置。只有缺档可以走新军团路径；失败时宿主阻止开始/继续保存，界面说明错误。不能从 `load_record() == {}` 推断不存在旧档。

写入顺序为：值拷贝与完整内存校验 → 写同目录临时文件并核实完整内容 → 备份原文件并核实备份 → 原子替换目标。失败清理本次临时文件并保留原档；备份不得因文件名碰撞被覆盖。至少保留既有可恢复备份，本项不自动清理用户备份。重复加载已升级 v4 不再迁移或改变兵力。

保存失败须返回明确结果，不能把失败展示为已保存。显式重置入口仍先归档原档；修复/迁移失败不得自动触发重置。测试全部使用隔离路径；故障覆盖包括坏 JSON、错误类型、未来版本、非法条目、备份失败、写入失败和替换失败，逐次比较原文件字节。
