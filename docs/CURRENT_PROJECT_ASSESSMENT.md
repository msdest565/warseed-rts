## 1. 执行摘要

当前项目不是空原型，而是一套已经打通的离线 2D RTS 指挥链技术切片：它拥有固定 10 Hz 权威模拟、统一命令校验、单位与建筑、采矿与生产、战争迷雾、编队、玩家接管/归队、我方 Agent 授权、敌方规则 AI、任务反馈和自动测试。

这套基础与新企划在“合法命令边界、Agent 可解释性、公平情报、玩家最终控制、编队执行”上高度一致，值得保留。主要偏差发生在产品表层和控制粒度：现有玩法围绕基地建设、矿车经济、单车选择与 5—15 个单位展开；新企划围绕常驻军团卡牌、资源区自动产出、部队卡级操作与约百个实体展开。

因此，正确路线不是推倒重写，也不是直接在现有 HUD 上贴卡牌皮肤，而是：保留模拟和命令内核，新增“军团编制领域层”和“会战规则层”，再把输入与 HUD 从单实体中心迁移到将领/部队卡中心。

## 2. 当前工程事实

### 2.1 技术基线

| 项目 | 当前状态 |
|---|---|
| 引擎 | Godot 4.6.3 stable，GL Compatibility |
| 语言 | typed GDScript |
| 平台 | Windows first，1280x720 设计视口，全屏启动 |
| 权威模拟 | 10 Hz `SimulationWorld`，表现层目标 120 FPS |
| 核心链路 | `Input / UI / Agent -> GameCommand -> Validator -> Queue -> SimulationWorld -> Snapshot/Event -> Presentation` |
| 运行方式 | 离线，不依赖 LLM、云服务或第三方插件 |
| 数据 | typed custom Resource 与文本 `.tres` |
| 测试 | 项目自有 headless runner，交接记录为 13 个测试套件 |

本次迁移使用锁定的 Godot 4.6.3 完成 editor import、13 套 headless tests、3600 tick 旧切片 smoke、主场景 smoke、1280x720 实际渲染、Windows debug export 和导出程序 headless 启动。完整结果见 `STATUS_AND_NEXT_STEPS.md`。

### 2.2 已实现的玩法基础

- 单位精确点选、框选、Shift 选择、控制组、移动、停止、攻击和移动攻击；
- 192x128 逻辑格（6144x4096、为上一版 4 倍面积）、AStarGrid2D、对角寻路、路径缓存、编队槽位、窄路纵队和卡住恢复；
- 五类单位：矿车、工程车、侦察车、突击车、导弹车；
- 三类建筑：指挥中心、无人兵工厂、前线支援站；
- 矿车往返采矿、工程车施工与维修、建筑占格、生产队列和退款；
- 权威弹丸、护甲、追击、自动接敌、死亡和残骸清理；
- 阵营战争迷雾、最后确认位置、情报残影和小地图警报；
- 发展、防守、攻击、侦察四类高层任务；
- 玩家接管、Agent 覆盖拒绝、明确 RETURN/STAY/JOIN/MANUAL 归属处理；
- 工业主管和战场将领四级授权，以及参谋部均衡/经济/固守/进攻方针；
- 规则驱动敌方八阶段循环和 Easy/Normal/Hard/Expert 数据化难度；
- 中英文 HUD、任务流程、受阻原因、路线、半径和调试层。

### 2.3 当前可玩形态

现有主场景是一张程序化占位风格的 2D 地图。玩家基地在左上，敌方基地在右下；底部是任务、战略、工程和生产指挥台，左侧显示工作流，左下为小地图，左上为资源。当前一局仍以采矿、建造、生产和摧毁指挥中心为核心。

这证明了“AI 与玩家通过同一命令链驱动真实单位”的技术可行性，但尚未证明“用常驻军团卡牌组织约百个实体”的目标体验。

## 4. 最有价值的可复用资产

### 4.1 权威边界

`SimulationWorld` 作为唯一战局真相，是迁移中最不应破坏的部分。卡牌拖放、将领改令、支援指令和部队阵线都应继续转换为 `GameCommand`，经验证后在 tick 边界生效。这样可以保留回放、测试、公平 AI 和稳定控制权。

### 4.2 控制权与归队

现有 `PLAYER_CONTROLLED / AGENT_ASSIGNED / TEMPORARILY_OVERRIDDEN / UNASSIGNED / DISABLED` 以及明确归队流程，已经解决了新企划最难的交互风险之一。迁移时应把控制对象从“单辆导弹车”升级为“完整部队卡及其实体集合”，而不是重新发明另一套控制权。

### 4.3 阵营知识与敌情记忆

当前可见敌军、最后确认位置、残骸和未知真值已经分离。新企划只需在接触记录上补充观测来源、估计数量、可信度、预计到达时间和置信衰减，就能支撑《灰脊矿区》的情报体验。

### 4.4 Agent 任务和解释层

现有任务生命周期、阶段、参与者、目标、路线、半径、受阻原因和决策原因可以成为具名将领 Agent 的骨架。将领性格和战法应修改任务选择、阈值和局部执行，不应绕过任务系统直接控制实体。

### 4.5 敌方规则 AI

现有敌人已经遵守阵营信息、命令管线、生产和战斗规则，也有反应延迟、撤退滞回、路线评分和固定数据配置。这使“锁定计划而不作弊”具有现实基础。需要改变的是组织方式：从通用八阶段经济循环转为场景加载时选定的计划模板、反应触发器与承诺时间。

## 5. 结构性缺口

### 5.1 缺少军团卡牌领域模型

当前 `UnitDefinition` 定义单个载具，`FormationState` 主要是即时编队状态；二者都不能表达持续部队卡的番号、编制、现员、所属将领、战损、经历、装备和战后存续。需要新增独立于表现层的军团数据模型。

建议最小模型：

```text
CommanderDefinition / CommanderState
  id, name, capacity, personality, specialties, doctrine_slots

UnitCardDefinition / UnitCardState
  id, unit_type, authorized_strength, current_strength
  member_entity_ids, commander_id, deployment_state
  morale, organization, losses, honors, equipment

DoctrineDefinition
  id, compatible_roles, behavior_constraints, tradeoffs

ArmyRosterState
  commanders, attached_unit_cards, headquarters_reserve
```

卡牌 UI 只消费这些状态的快照，不能成为第二份编制真相。

### 5.2 当前最低操作粒度不符合新目标

现有输入强调精确单选、局部框选和单车接管，而新企划明确不逐个士兵微操。首个新切片应默认禁用个体选择，把地图点击解析为所属部队卡；调试模式可以保留个体选择，用于开发和定位，但不能作为正式玩法依赖。

### 5.3 经济循环需要并行的新规则集

当前矿车、建筑和生产系统功能完整，但《灰脊矿区》要求资源区每 30 秒自动结算、基础补给收入、预备编制部署和支援花费。建议保留旧系统代码，不在第一步删除；为场景增加 `BattleEconomyMode` 或等价规则配置，使会战场景不生成矿车经济链。

### 5.4 多军团并行尚未成立

交接文档明确指出当前只支持工业、侦察和一个主力作战任务稳定并行，尚无多个独立主力战斗编队和任意任务图。《灰脊矿区》至少需要中央、西部和东部三个方向同时存在任务承诺，因此多将领、多部队卡、独立目标和增援迁移是 P0。

### 5.5 百实体规模未经验证

当前导航方案和文档预算以 10—15 个单位为目标。新企划的 60—120 个实体不能直接假定可用。主要风险包括：每实体全局 A*、分离计算、弹丸数量、快照复制、HUD 同步和 Agent 逐实体决策。

建议先做三档无 UI 压测：40、80、120 个实体，记录 10 Hz tick 的平均值、P95 和最坏值，再决定是否引入分层更新、编队共享路径、空间索引或更轻的远距模拟。

### 5.6 地形目前主要是通行信息

新企划要求开阔地、废墟、林地、高地和据点直接改变发现、展开与战斗。当前逻辑格主要记录阻挡和导航，尚缺少稳定的地形战术标签。应先实现少量可解释规则：掩体、视野遮蔽、装甲展开、突击近战和火力射界，不要先堆复杂伤害类型。

## 6. 推荐迁移路线

### 阶段 0：冻结三个产品决策

在继续扩充现有基地 RTS 前，把以下结论写入决策记录并视为新切片验收边界：

1. 核心卡牌全部常驻，不抽牌；
2. 正式玩法最低直接操作单位是一张部队卡，不是单体实体；
3. 首个新切片使用资源区自动产出与预备部队部署，不使用矿车经济。

退出条件：旧文档中的“完整传统 RTS 单位微操”和新企划不再同时被描述为同一个 MVP 的硬目标。

### 阶段 1：建立军团模型，不先重做战斗

- 新增将领、部队卡、战法和军团编制的 typed Resource/State/Snapshot；
- 用一张部队卡包装一组现有 `UnitState`；
- 战损从实体汇总到部队卡；
- 增加将领到部队卡的所有权和容量验证；
- 保持现有移动、弹丸、视野和伤害系统不变。

退出条件：测试中一张“铁壁突击群”卡能生成并持续关联 12 个实体，损失 3 个后卡面现员稳定显示 9，保存/重载后 ID 不变。

### 阶段 2：做常驻军团板与部队卡级控制

- 用新军团板替换当前底部生产中心布局；
- 实现将领卡拖到区域、部队卡选择、路线绘制、阵线绘制和明确归还；
- 正式输入不允许选择单个成员；
- 卡牌与战场实体、路线、任务和战损双向高亮。

退出条件：玩家只通过两张将领卡和三张部队卡，能够完成部署、改令、直接控制一支编队并归还，全程无需个体选择。

### 阶段 3：实现《灰脊矿区》会战规则

- 新建三资源区和南北总部地图；
- 实现基础补给、30 秒区域结算、人口和 10 秒预备部署；
- 实现装甲、突击、火力、侦察四类战团和最小地形规则；
- 增加空中侦察与紧急筑垒支援指令；
- 实现开局 00:20 情报与距离提示；
- 敌方计划、触发器和反应延迟由场景数据锁定。

退出条件：同一初态、种子和命令序列可重复得到一致的关键占点、接敌和胜负结果；A/B/C 只是三种可行操作组合，系统也接受其他合法组合。

### 阶段 4：多将领 Agent 与战法

- 将现有战场主管拆成具名将领实例；
- 将性格、姿态和战法编译为任务约束、阈值和目标评分修正；
- 支持至少两支主力和一支侦察部队独立并行；
- 所有自主改令显示触发原因和使用的情报。

退出条件：相同部队分别交给谨慎和激进将领时，在同一情报下产生稳定、可解释且不同的接敌/撤退行为。

### 阶段 5：规模与战后回写

- 完成 40/80/120 实体性能基线；
- 优化编队共享路径、决策频率和快照成本；
- 把现员、损失、经历和一项荣誉回写到持久部队卡；
- 完成一局到战后整编的最短闭环。

退出条件：目标硬件上 80—100 实体保持权威 tick 预算，且玩家能在第二局看到第一局造成的真实部队差异。

## 7. 首个开发增量建议

不建议第一步同时改 UI、经济、AI、地图和百实体性能。最短的高价值增量是“部队卡外壳”：

1. 新增一名测试将领和两张部队卡；
2. 每张卡绑定一组现有单位实体；
3. 卡面显示现员、位置、任务和控制者；
4. 点击卡牌选中整组实体；
5. 地图命令按组提交；
6. 现有单体接管只在调试模式保留；
7. 用自动测试验证成员死亡、任务分配、接管和归还不会破坏卡牌状态。

这个增量能最快回答最重要的问题：卡牌是否真的成为军队与战场之间的操作入口，而不是新皮肤。

## 8. 文档一致性建议

现有文档仍把“完整传统 RTS 操作、矿车采集、基地建设、10—15 个单位”定义为 MVP。整合企划则把“常驻军团卡牌、自动资源区、部队卡级操作、约百实体”定义为产品核心。两者目前是明确冲突，不应通过模糊措辞同时保留。

建议在用户确认新企划为正式方向后，依次更新：

1. `DECISIONS.md`：新增一条 Accepted 产品转向决策；
2. `PRODUCT_VISION.md`：改写一句话定义、玩家幻想和控制粒度；
3. `MVP_SCOPE.md`：用《灰脊矿区》替换当前矿车/基地切片；
4. `SYSTEM_DESIGN.md`：新增军团编制领域层和部队卡控制权；
5. `ROADMAP.md`：把军团模型、常驻卡牌板和多将领并行前置；
6. `STATUS_AND_NEXT_STEPS.md`：保留现有技术成果，但明确其作为迁移基础而非新企划完成度。

本次只新增企划与评估文档，没有擅自把既有 Accepted 决策改写为已确认的新方向。

## 9. 初步结论

当前项目已经证明底层“可执行指挥链”，并形成《灰脊矿区》首个工程可玩切片：三名具名将领、四张稳定部队卡、整卡航路/阵线、会战经济、战法、地形情报、公平敌方反应和最小跨局战损都已闭合。开局为 20 个友方加 14 个敌方实体，满预备投入时场上达到 48 个实体，独立基准覆盖 40/80/120 实体。

项目尚未证明的是完整产品验收：陌生玩家是否能在 30 秒内理解并下令，目标硬件完整渲染是否稳定，当前补员/荣誉/装备取舍是否真的促成第二局意愿，以及三套敌方计划能否支撑足够的重玩价值。下一阶段应围绕这些试玩证据收敛，不继续扩充旧基地经济广度。
