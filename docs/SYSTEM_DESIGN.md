# 系统设计

> 本文已按 D-017 迁移到常驻军团卡牌方向。矿车、建筑和工业主管相关实现是可复用的旧技术能力，不属于《灰脊矿区》P0。

## 设计目标

系统要保证“军团卡牌 -> 将领意图 -> 部队卡任务 -> 真实实体动作 -> 战损回写”形成单一权威闭环，同时让玩家随时拥有最终控制权。MVP 优先采用 typed 军团数据、可测试任务模板、规则调度和状态机；语言模型未来只能把自然语言转换成受验证的结构化意图。

## 分层架构

```text
玩家输入层
├─ 将领卡意图
├─ 部队卡路线／阵线命令
└─ 预备队与支援指令
        ↓
军团编制层
├─ 将领、容量、性格与战法槽
├─ 部队卡、成员实体与持续战损
└─ 总部预备编制
        ↓
目标与任务层
├─ 战略目标
├─ 将领 Agent 任务
├─ 部队卡任务
└─ 实体安全动作
        ↓
控制权仲裁层
├─ 单位归属
├─ 玩家临时接管
├─ 命令优先级
└─ 暂停、取消与恢复
        ↓
Agent 决策层
├─ 主 AI／参谋长
├─ 多名具名将领
└─ 部队局部 Agent
        ↓
游戏模拟层
├─ 移动与战斗
├─ 战略区域与补给
├─ 预备部署与支援
└─ 视野、情报与地形
        ↓
反馈层
├─ 目标、路线与编队标记
├─ 任务状态与受阻原因
├─ 敌情与事件记录
└─ 警报和摘要
```

## Godot 实现映射

详细实现基线见 [Godot 技术方案](TECHNICAL_PLAN.md)。抽象分层在 Godot 中映射为：

```text
InputController / HUD / Agent
        ↓
GameCommand → CommandValidator → CommandQueue
        ↓
SimulationHost → SimulationWorld
        ↓
SimulationEvent / WorldSnapshot
        ↓
WorldPresentation / HUD / DebugLayer
```

`SimulationWorld` 保存唯一权威状态，包含将领、部队卡、成员实体、任务、区域和资源。卡牌使用稳定定义 ID，实体使用稳定 `EntityId`；HUD 只消费快照，不能自行维护现员、战损、部署或隶属关系。

## 权威边界

Agent 与玩家界面都必须实例化同一类 `GameCommand`，并通过同一个 `CommandValidator` 影响模拟，例如将领目标、部队卡移动/攻击/阵线、投入预备队和请求支援。旧采集、生产和施工命令继续遵守同一边界，但不属于新切片成功路径。

Agent 不得：

- 直接改变卡牌隶属、实体位置、生命、现员或资源；
- 跳过建造和生产时间；
- 读取玩家尚未获得的精确敌军信息；
- 在部队卡被玩家接管后继续发送覆盖命令；
- 用自由文本直接驱动未经验证的底层动作。

这条边界使行为可回放、可调试、可取消，也便于未来进行同步和自动测试。

## 模拟步进与处理顺序

- `SimulationWorld` 初始以 10 Hz 固定 `SimulationTick` 推进，渲染目标为 60 FPS并在快照之间插值；
- 输入逐帧采集，但只转换为命令，不能直接修改模拟；
- 模拟使用项目封装的固定种子随机源，表现随机与模拟随机分离；
- 同一 tick 集中按“命令与控制权 → 任务/意图 → 移动 → 经济/生产 → 战斗/死亡 → 胜负 → 事件/快照”处理；
- 结算不得依赖 SceneTree 遍历顺序；
- 10 Hz 是初始可测量基线，若手感或精度不足，应统一调整并更新决策记录。

## 导航与编队边界

首个新切片继续使用独立逻辑格和 `AStarGrid2D`，但全局路径按部队卡/formation 共享，成员只处理槽位、简单 separation、卡住恢复和窄路降级。40/80/120 实体必须建立性能基线，不能沿用旧 10—15 单位预算作无测量推断。

玩家正式接管整张部队卡；成员保持卡牌归属，但将领不能继续下令。归还时部队选择安全 rejoin point，禁止瞬移。个体接管逻辑只保留作开发诊断和旧技术回归。

## 命令优先级

优先级从高到低：

1. 玩家紧急停止或脱离；
2. 玩家部队卡级直接命令；
3. 玩家将领级意图；
4. 将领 Agent 当前任务；
5. 部队局部 Agent 与实体安全行为。

高优先级命令发生时，低优先级任务必须暂停或重新规划，不能在下一帧抢回控制权。

## 部队卡与实体控制状态

正式控制权记录在部队卡，成员实体继承并执行。现有每实体状态继续作为内部仲裁基础：

- `PlayerControlled`：由玩家持续管理；
- `AgentAssigned`：归指定 Agent 和任务管理；
- `TemporarilyOverridden`：原属 Agent，但已被玩家临时接管；
- `Unassigned`：可用但尚无任务；
- `Disabled`：死亡、失能或处于不可接受命令的状态。

部队卡还要记录所属将领、成员实体、当前控制者、原任务、最后合法命令、接管原因和可归还目标。卡面现员必须从成员实体计算。

### 接管流程

1. 玩家选中 Agent 管理的部队卡并发出直接命令；
2. 卡牌及存活成员进入 `TemporarilyOverridden`；
3. 原将领保留组织关系，但从当前任务可调度对象中排除该卡；
4. 玩家继续操作，Agent 不覆盖命令；
5. 玩家选择归还原将领、转隶、留在当前位置或继续手动；
6. 归还时整队选择安全集结点，恢复任务而非瞬移。

不得使用几秒无操作后自动抢回的隐式机制。

## 三层任务模型

### 战略目标

由玩家决定“要什么”，例如控制中央中继站、从西侧牵制、保留装甲预备队或摧毁敌方总部。

### Agent 任务

由参谋长与具名将领按模板拆解，例如搜索东部林地、在中央废墟展开、为火力群建立视野、投入预备队或组织撤退。

### 部队与实体动作

由部队卡与成员实体执行共享路线、槽位移动、建立射界、攻击指定目标、保持距离、近距自卫和撤退等动作。

参谋长不越过中间层逐 tick 操作实体；成员实体不自行改变上层目标。

## 任务生命周期

每项高层目标和 Agent 任务使用统一状态：

- `Waiting`：等待资源、单位或前置任务；
- `Preparing`：预留资源、选址、分配单位或集结；
- `Executing`：正在执行；
- `Paused`：被玩家或高优先级任务暂停；
- `Blocked`：当前无法推进；
- `Completed`：满足验收条件；
- `Failed`：已无法完成且没有安全恢复方案；
- `Cancelled`：被玩家或上层任务取消。

`Blocked` 必须给出机器可读原因和用户可读说明，例如资源不足、没有可用工程车、路径不可达、编队人数不足、目标威胁过高或关键单位被玩家接管。

任务支持暂停、取消、修改目标、调整参与单位、调整优先级和修改撤退条件。

## 资源与目标冲突

### 全局优先级

玩家通过主攻方向、将领姿态和预备队投入表达优先级。补给不足、人口不足或同一部队卡被多个任务申请时，按“玩家直接命令 > 玩家意图 > 已承诺任务 > Agent 机会任务”仲裁，不频繁弹窗。

### 资源预留

任务记录补给成本、已承诺资源、人口、部署时间、当前缺口和开始条件。总部预备队投入和支援指令共享补给账本；已经开始部署的部队具有短期承诺窗口，不能被 Agent 反复取消重投。

只有两个明确的高层目标无法同时满足、且既定优先级不能解决时，参谋长才请求玩家选择。

## 主 AI／参谋长

职责：

- 校验玩家高层命令；
- 选择预定义任务模板并分派给对应 Agent；
- 汇总补给、人口、预备队、敌情、部队卡和受阻状态；
- 检测跨 Agent 冲突；
- 向玩家报告需要决策的异常。

MVP 不实现任意自由规划器。“控制中央中继站”等目标使用可检查的任务图：侦察、评估威胁、选择将领、集结部队卡、沿路线推进、展开、建立控制、持续监控。

## 旧工业主管（非《灰脊矿区》P0）

现有工业主管维护矿区、矿车、工程车、建筑、损伤、生产队列和资源预算。这些能力继续保留和回归，但不进入新切片成功路径。

第一版能力：

- 将矿车分配到指定矿区并循环采集；
- 遇敌时向已知安全点撤退；
- 管理指定生产计划；
- 在玩家指定区域内选择合法建筑位置；
- 显示蓝图后调度工程车施工；
- 报告资源、路径和单位受阻原因。

维修优先级和复杂经济优化在基础流程稳定后加入。

## 具名战场将领

每张将领卡维护所属部队卡、容量、性格、战法、当前任务、最近接敌位置、敌军估算和损失。

第一版能力：

- 同时管理一个或多个已挂载部队卡；
- 前往集结点；
- 防守指定区域且不追击超过半径；
- 沿玩家指定路线攻击目标；
- 按战法与部队角色建立前后排、观察点和展开阵线；
- 达到损失阈值时撤退并报告；
- 在整张部队卡被接管后降级任务，并等待明确归还。

进攻、防守和撤退条件必须数据化，避免不可解释的随机切换。

## 部队局部 Agent 与基础实体

部队局部 Agent 和实体安全状态机只完成下层执行：

- 侦察成员：移动、观察、隐蔽、避战和报告；
- 突击成员：占用掩体、保持前排、近距接敌和清理据点；
- 火力成员：保持射界、接受目标分配并避免被接近；
- 装甲成员：保持展开间隔、正面推进和有限追击；
- 工程/防空成员：围绕所属部队提供局部支援。

默认安全行为只处理迫在眉睫的局部危险，不能自行改变上层目标。

## 敌情与战争迷雾

玩家方 Agent 只能使用：

- 当前视野中的敌人；
- 已探索地形；
- 敌人最后已知位置、时间和当时兵力；
- 由侦察任务产生的报告。

报告要表达不确定性，例如“西侧路线 45 秒未侦察”，而不是把未知信息伪装成事实。

## 可解释反馈

每项活动中的任务至少显示：

- 发起者与负责 Agent；
- 战略目标和当前阶段；
- 参与单位与缺员情况；
- 地图目标、集结点和计划路线；
- 资源预算与预计开始条件；
- 撤退或完成条件；
- 最近重要事件；
- 暂停、受阻或失败原因；
- 可用的暂停、取消、修改和接管操作。

普通状态变化进入事件记录；只有基地受袭、关键任务失败、严重目标冲突等事件使用强警报。

## 可测试性要求

- 纯 `SimulationWorld` 测试无需加载主游戏场景；
- 任务模板、阈值与单位属性使用 typed custom `Resource` 和文本 `.tres`；
- 固定随机种子、初态和命令序列应产生相同关键状态/事件摘要；
- 命令、控制权转换和任务状态变化写入结构化事件日志；
- 支持 Godot headless 加速运行经济、战斗和敌方阶段流程，并返回可靠退出码；
- 对 UI 和 Agent 参数化测试，证明二者经过相同 `CommandValidator`；
- 自动测试覆盖命令优先级、资源预留、接管归队、任务取消、不可达路径与 Agent 不作弊；
- GUT 仅是待技术 spike 的候选，兼容性验证前不作为已采用依赖。

## 仍待验证的问题

- Windows 最低硬件和正式性能预算；
- 10 Hz 是否满足最终移动与战斗手感；
- GUT 是否正式采用及固定版本；
- 局部避障是否达到升级触发条件；
- 完整回放格式与未来多人同步边界；
- 美术资产来源、许可和 Git LFS 启用阈值；
- 自然语言功能进入 post-MVP 的条件。
