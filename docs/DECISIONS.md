# 决策记录

本文件用于记录项目早期的重要产品与技术决策。状态可为：`Proposed`、`Accepted`、`Rejected`、`Superseded`。

## D-001：采用文档优先的仓库基线

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目已有详细产品构想，但尚未选择引擎、语言或平台，当前目录为空。
- **决策**：首个提交只包含产品愿景、MVP 范围、系统设计、路线图和通用仓库配置，不创建实现代码或引擎工程。
- **理由**：避免因假设技术栈产生返工，让后续选型有明确需求依据。
- **后果**：下一阶段必须先完成引擎评估，之后才能建立代码结构。

## D-002：GitHub 仓库策略

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：仓库为 `msdest565/warseed-rts`，可见性为 Private，默认分支为 `main`。
- **理由**：产品概念尚未公开，先保护设计与技术规划；未来可主动改为公开。
- **后果**：远程创建后必须验证所有者、可见性和默认分支。

## D-003：暂不添加开源许可证

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：代码、美术、音频、名称与设计文档的开放策略尚未确定。
- **决策**：初始仓库不包含 `LICENSE`。
- **理由**：避免在商业与协作模式未明确前授予过宽权利。
- **后果**：默认保留全部权利；若未来公开或引入协作者，需要单独决定代码与资产许可。

## D-004：中文正文与英文稳定标识

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：首批文档使用中文正文，文件名、代码标识和状态枚举使用英文。
- **理由**：保证当前设计沟通效率，同时为未来实现与国际协作保留稳定命名。
- **后果**：术语在不同文档间应保持一致，若以后翻译则避免复制出分叉规格。

## D-005：玩家拥有最终控制权

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目核心是委托与微操共存，而非自动播放。
- **决策**：命令优先级为“玩家直接命令 > 玩家高层命令 > Agent 任务 > 单位默认行为”；玩家接管后，Agent 直到明确归队前不得覆盖该单位。
- **理由**：建立可预测的控制权，避免玩家与 Agent 抢操作。
- **后果**：所有单位和任务必须记录控制者、归属、暂停原因与归队目标。

## D-006：Agent 通过统一命令边界行动

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：玩家界面和 Agent 都通过同一套合法游戏命令改变模拟；Agent 不直接修改位置、资源、生命或战斗结果。
- **理由**：提高可测试性、可解释性、回放能力和未来同步的可行性。
- **后果**：模拟、命令校验、Agent 决策和表现层必须解耦。

## D-007：MVP 不依赖语言模型

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：首要验证是委托、透明度和控制权，而非自然语言理解。
- **决策**：MVP 使用结构化命令、任务模板、规则调度和状态机。语言模型若以后加入，只把自然语言转换为受验证的结构化目标。
- **理由**：降低不确定性、成本与调试范围，并保证离线核心玩法成立。
- **后果**：不得把模型输出直接用作底层单位命令。

## D-008：第三种建筑定义为前线支援站

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：原“雷达／维修站”统一命名为“前线支援站”，在 MVP 中兼具扩大视野和范围维修能力。
- **理由**：保持三建筑范围，同时让复合功能具有统一的前线据点定位。
- **后果**：侦察车仍是主动获取视野的主要单位；支援站提供固定区域价值。

## D-009：引擎、语言与目标平台延期决定

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：仓库初始化时不选择 Godot、Unity、Unreal 或其他方案，也不创建对应项目。
- **理由**：需要以 RTS 工作流、导航编队、UI、可测试性、平台、许可和团队熟悉度进行评估。
- **后果**：下一阶段产出候选评分矩阵和小型技术验证，再在本文件记录最终选择。
