# 决策记录

本文件用于记录项目早期的重要产品与技术决策。状态可为：`Proposed`、`Accepted`、`Rejected`、`Superseded`。

## D-001：采用文档优先的仓库基线

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目已有详细产品构想，但尚未选择引擎、语言或平台，当前目录为空。
- **决策**：首个提交只包含产品愿景、MVP 范围、系统设计、路线图和通用仓库配置，不创建实现代码或引擎工程。
- **理由**：避免因假设技术栈产生返工，让后续选型有明确需求依据。
- **后果**：该初始化阶段已完成；后续代码结构遵循 D-010 至 D-013 的 Godot 技术基线建立。

## D-002：GitHub 仓库策略

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：仓库为 `msdest565/warseed-rts`，可见性为 Private，默认分支为 `main`。
- **理由**：产品概念尚未公开，先保护设计与技术规划；未来可主动改为公开。
- **后果**：远程创建后必须验证所有者、可见性和默认分支。

## D-003：暂不添加开源许可证

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：代码、美术、音频、名称与设计文档的开放策略尚未确定。
- **决策**：初始仓库不包含 `LICENSE`。
- **理由**：避免在商业与协作模式未明确前授予过宽权利。
- **后果**：默认保留全部权利；若未来公开或引入协作者，需要单独决定代码与资产许可。

## D-004：中文正文与英文稳定标识

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：首批文档使用中文正文，文件名、代码标识和状态枚举使用英文。
- **理由**：保证当前设计沟通效率，同时为未来实现与国际协作保留稳定命名。
- **后果**：术语在不同文档间应保持一致，若以后翻译则避免复制出分叉规格。

## D-005：玩家拥有最终控制权

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目核心是委托与微操共存，而非自动播放。
- **决策**：命令优先级为“玩家直接命令 > 玩家高层命令 > Agent 任务 > 单位默认行为”；玩家接管后，Agent 直到明确归队前不得覆盖该单位。
- **理由**：建立可预测的控制权，避免玩家与 Agent 抢操作。
- **后果**：所有单位和任务必须记录控制者、归属、暂停原因与归队目标。

## D-006：Agent 通过统一命令边界行动

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：玩家界面和 Agent 都通过同一套合法游戏命令改变模拟；Agent 不直接修改位置、资源、生命或战斗结果。
- **理由**：提高可测试性、可解释性、回放能力和未来同步的可行性。
- **后果**：模拟、命令校验、Agent 决策和表现层必须解耦。

## D-007：MVP 不依赖语言模型

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：首要验证是委托、透明度和控制权，而非自然语言理解。
- **决策**：MVP 使用结构化命令、任务模板、规则调度和状态机。语言模型若以后加入，只把自然语言转换为受验证的结构化目标。
- **理由**：降低不确定性、成本与调试范围，并保证离线核心玩法成立。
- **后果**：不得把模型输出直接用作底层单位命令。

## D-008：第三种建筑定义为前线支援站

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：原“雷达／维修站”统一命名为“前线支援站”，在 MVP 中兼具扩大视野和范围维修能力。
- **理由**：保持三建筑范围，同时让复合功能具有统一的前线据点定位。
- **后果**：侦察车仍是主动获取视野的主要单位；支援站提供固定区域价值。

## D-010：采用 Godot、typed GDScript 与 Windows-first

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：WARSEED 当前是小规模 2D RTS，首要风险是控制权、任务透明度和快速玩法验证，而非大规模渲染或单位性能。
- **决策**：采用 Godot 4.6 stable 系列、typed GDScript、2D top-down 和 Windows 10/11 x86-64 first。工程创建时锁定最新 `4.6.x-stable` 精确补丁，编辑器、测试与导出模板保持一致。
- **理由**：Godot 的原生 2D、UI、自定义绘制、文本资源和轻量迭代最符合首个垂直切片；Unity 与 Unreal 在当前阶段的额外工程负担没有带来决定性收益。
- **后果**：patch 升级需独立提交并完成回归；跨 minor 升级需新决策。下一阶段建立最小 Godot 工程，不再进行引擎选型。

## D-011：分离固定步进权威模拟与 Godot 表现层

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：`SimulationWorld` 以初始 10 Hz 固定 tick 保存和推进唯一权威状态；Godot 节点、UI、动画与音频只消费 `WorldSnapshot` 和 `SimulationEvent`。输入与 Agent 均通过共享 `GameCommand`、`CommandValidator` 和 `CommandQueue` 影响模拟。
- **理由**：避免核心规则依赖渲染帧或 SceneTree 顺序，并保证控制权、测试、事件解释和固定种子复现。
- **后果**：核心规则不得散落在单位节点的 `_process()` 中；10 Hz 若经测量不足，必须统一修改并更新决策，而非各系统自行选频率。

## D-012：采用 TileMapLayer、AStarGrid2D 与自定义 formation slots

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：`TileMapLayer` 用于地图编辑和表现，独立逻辑格保存通行与战略信息；首个切片使用 `AStarGrid2D` 做静态全局寻路，并实现自定义 formation slots、简单 separation、卡住检测和狭窄通道纵队降级。
- **理由**：该方案足以支持 10—15 个 MVP 单位，行为可预测且便于测试，无需提前引入流场或复杂动态导航。
- **后果**：只有在 MVP 规模下仍长期拥堵、频繁重算超预算或动态障碍产生大量错误路径时，才评估 `NavigationServer2D`、流场或更复杂局部避障。

## D-013：采用 typed Resource、headless 测试与初期 no-LFS

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：静态游戏数据使用 typed custom `Resource` 和文本 `.tres`；测试分为纯模拟、Godot headless 集成和场景试玩三层。GUT 仅作为待 spike 候选。初期不启用 Git LFS，Godot 专用忽略规则随真实工程一起加入。
- **理由**：保持配置可审查、运行状态与静态数据分离，并避免在依赖和二进制资产尚不存在时增加维护成本。
- **后果**：工程 bootstrap 必须验证 headless 退出码、数据引用校验和 Windows 导出；GUT 通过兼容性验证后才能锁定版本，大型文件策略需在真实资产增长后重新决策。
