# 决策记录

本文件用于记录项目早期的重要产品与技术决策。状态可为：`Proposed`、`Accepted`、`Rejected`、`Superseded`。

## D-001：采用文档优先的仓库基线

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目已有详细产品构想，但尚未选择引擎、语言或平台，当前目录为空。
- **决策**：首个提交只包含产品愿景、MVP 范围、系统设计、路线图和通用仓库配置，不创建实现代码或引擎工程。
- **理由**：避免因假设技术栈产生返工，让后续选型有明确需求依据。
- **后果**：该初始化阶段已完成；后续代码结构遵循 D-010 至 D-013 的 Godot 技术基线建立。

## D-004：中文正文与英文稳定标识

- **状态**：Accepted

## D-005：玩家拥有最终控制权

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：项目核心是委托与微操共存，而非自动播放。
- **决策**：命令优先级为“玩家直接命令 > 玩家高层命令 > Agent 任务 > 单位默认行为”；玩家接管后，Agent 直到明确归队前不得覆盖该单位。
- **理由**：建立可预测的控制权，避免玩家与 Agent 抢操作。
- **后果**：所有单位和任务必须记录控制者、归属、暂停原因与归队目标。

## D-006：Agent 通过统一命令边界行动

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：玩家界面和 Agent 都通过同一套合法游戏命令改变模拟；Agent 不直接修改位置、资源、生命或战斗结果。
- **理由**：提高可测试性、可解释性、回放能力和未来同步的可行性。
- **后果**：模拟、命令校验、Agent 决策和表现层必须解耦。

## D-007：MVP 不依赖语言模型

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：首要验证是委托、透明度和控制权，而非自然语言理解。
- **决策**：MVP 使用结构化命令、任务模板、规则调度和状态机。语言模型若以后加入，只把自然语言转换为受验证的结构化目标。
- **理由**：降低不确定性、成本与调试范围，并保证离线核心玩法成立。
- **后果**：不得把模型输出直接用作底层单位命令。

## D-008：第三种建筑定义为前线支援站

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：原“雷达／维修站”统一命名为“前线支援站”，在 MVP 中兼具扩大视野和范围维修能力。
- **理由**：保持三建筑范围，同时让复合功能具有统一的前线据点定位。
- **后果**：侦察车仍是主动获取视野的主要单位；支援站提供固定区域价值。

## D-010：采用 Godot、typed GDScript 与 Windows-first

- **状态**：Accepted
- **日期**：2026-07-30
- **背景**：WARSEED 当前是小规模 2D RTS，首要风险是控制权、任务透明度和快速玩法验证，而非大规模渲染或单位性能。
- **决策**：采用 Godot `4.6.3.stable.mono.official.7d41c59c4`、typed GDScript、2D top-down 和 Windows 10/11 x86-64 first。仓库通过 `.godot-version` 锁定 `4.6.3-stable`；编辑器、测试与导出模板保持同一精确版本。当前使用 Mono 编辑器不改变项目仅采用 typed GDScript 的语言基线。
- **理由**：Godot 的原生 2D、UI、自定义绘制、文本资源和轻量迭代最符合首个垂直切片；Unity 与 Unreal 在当前阶段的额外工程负担没有带来决定性收益。
- **后果**：patch 升级需独立提交并完成回归；跨 minor 升级需新决策。下一阶段建立最小 Godot 工程，不再进行引擎选型。

## D-011：分离固定步进权威模拟与 Godot 表现层

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：`SimulationWorld` 以初始 10 Hz 固定 tick 保存和推进唯一权威状态；Godot 节点、UI、动画与音频只消费 `WorldSnapshot` 和 `SimulationEvent`。输入与 Agent 均通过共享 `GameCommand`、`CommandValidator` 和 `CommandQueue` 影响模拟。
- **理由**：避免核心规则依赖渲染帧或 SceneTree 顺序，并保证控制权、测试、事件解释和固定种子复现。
- **后果**：核心规则不得散落在单位节点的 `_process()` 中；10 Hz 若经测量不足，必须统一修改并更新决策，而非各系统自行选频率。

## D-012：采用 TileMapLayer、AStarGrid2D 与自定义 formation slots

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：`TileMapLayer` 用于地图编辑和表现，独立逻辑格保存通行与战略信息；首个切片使用 `AStarGrid2D` 做静态全局寻路，并实现自定义 formation slots、简单 separation、卡住检测和狭窄通道纵队降级。
- **理由**：该方案足以支持 10—15 个 MVP 单位，行为可预测且便于测试，无需提前引入流场或复杂动态导航。
- **后果**：只有在 MVP 规模下仍长期拥堵、频繁重算超预算或动态障碍产生大量错误路径时，才评估 `NavigationServer2D`、流场或更复杂局部避障。

## D-013：采用 typed Resource、headless 测试与初期 no-LFS

- **状态**：Accepted
- **日期**：2026-07-30
- **决策**：静态游戏数据使用 typed custom `Resource` 和文本 `.tres`；测试分为纯模拟、Godot headless 集成和场景试玩三层。GUT 仅作为待 spike 候选。初期不启用 Git LFS，Godot 专用忽略规则随真实工程一起加入。
- **理由**：保持配置可审查、运行状态与静态数据分离，并避免在依赖和二进制资产尚不存在时增加维护成本。
- **后果**：工程 bootstrap 必须验证 headless 退出码、数据引用校验和 Windows 导出；GUT 通过兼容性验证后才能锁定版本，大型文件策略需在真实资产增长后重新决策。

## D-014：当前 MVP 保留项目自有 headless runner

- **状态**：Accepted
- **日期**：2026-08-01
- **背景**：阶段 1 已有六个 typed GDScript 测试套件，覆盖命令、模拟、导航编队、观测指标、typed Resource 和主场景集成；现有 runner 能在锁定 Godot 版本下可靠返回进程退出码。仓库尚未引入 GUT 或其他 addon。
- **决策**：当前 MVP 继续使用项目自有最小 headless runner，不引入或 vendoring GUT。
- **理由**：现有测试规模下，迁移只会增加插件版本、导入和维护面，尚未带来明确的 fixture、参数化、过滤、诊断或 CI 报告收益。
- **后果**：当测试维护实际受到 fixture 生命周期、参数化、断言诊断、选择性运行或机器可读 CI 报告限制时，再重新评估并固定 GUT 兼容版本；此前不为更换框架阻塞路线图。

## D-015：首个战斗切片采用显式集火和死亡 tombstone

- **状态**：Accepted
- **日期**：2026-08-03
- **决策**：首个权威战斗切片只实现玩家显式指定敌方目标；射程外保持锁定但不追击，固定 tick 内按稳定实体顺序收集后统一结算伤害。死亡实体不立即从权威字典和快照删除，而保留为 disabled、零生命 tombstone。
- **理由**：先验证 AttackCommand、控制权、冷却、伤害、死亡事件、快照和表现的完整边界，避免同时引入追击、自动索敌、弹道、战争迷雾和敌方 AI。tombstone 让死亡表现、历史快照和确定性测试保持简单稳定。
- **后果**：AttackMove 当前仍只有移动意图；自动接敌、追击/脱战、尸体清理和武器数据资源化在 Phase 2 后续增量实现。Stop 或移动命令会取消显式攻击目标。

## D-016：战斗切片采用数据化弹丸、追击和 AttackMove 自动接敌

- **状态**：Accepted
- **日期**：2026-08-03
- **决策**：武器战斗参数进入 typed Resource；攻击在射程内生成权威弹丸，按弹丸速度飞行并在命中时使用 `max(1, attack_power - armor)` 结算。显式 Attack 在射程外追击，AttackMove 只在路线附近自动索敌并暂停交战，目标失效后恢复原路线。
- **理由**：修复“攻击命令只停止单位但没有攻击效果”的体验缺陷，同时保留固定 10 Hz、确定性快照和统一权威边界。
- **后果**：本轮仍不实现弹丸地形碰撞、伤害类型、敌方 AI 或远距离脱战规则；这些属于后续战斗扩展。

## D-017：核心产品转向常驻军团卡牌与部队卡级会战

- **状态**：Accepted
- **日期**：2026-08-08
- **背景**：现有技术切片已经证明基地经营、单实体 RTS 操作和可执行 Agent 指挥链，但没有充分表达项目真正独特的军团编成、将领性格、持续部队和战团级指挥体验。
- **决策**：正式产品以 [整合版游戏企划书](GAME_DESIGN_DOCUMENT.md) 为准。将领卡、部队卡、战法卡、荣誉与装备卡全部常驻且持续存在，不采用抽牌、洗牌或随机战斗手牌。正式玩法最低直接操作粒度为一张部队卡及其完整编队；个体选择只保留为开发诊断能力。首个新垂直切片为《灰脊矿区》，使用资源区自动产出、总部预备编制和支援指令，不使用矿车采集作为核心经济。
- **理由**：卡牌只有同时承担组织关系、Agent 解释方式、战场控制入口和跨局成长，才不是 UI 皮肤；部队卡级控制也更符合“比宏观大战略多一点、比传统全战少很多”的目标粒度。
- **后果**：现有权威模拟、统一命令、公平情报、任务解释、编队、接管归队和规则 AI 继续复用；产品愿景、MVP、路线图和 UI 逐步迁移。矿车、基地建设、逐单位生产和个体输入不再是新切片 P0，但代码暂不删除，可作为技术资产、调试能力或未来独立模式基础。

## D-026：取消真人证据硬门

- **状态**：Accepted
- **日期**：2026-09-07
- **背景**：现有真人 cohort 长期无法形成，而产品负责人已审查开发者试玩与工程证据，并明确要求取消真人证据要求、继续玩法改写。
- **决策**：真人试玩、访谈、问卷和观察员评估改为可选产品研究，不再作为工程实现、阶段出口、发布候选或进入后续阶段的必需证据。历史 `HUMAN`、`SIMULATED` 与 `NOT_RUN` 标签继续保留以说明证据来源，自动化不得被描述成真人体验结论。
- **理由**：让开发节奏由可重复的工程证据和明确产品决策驱动，同时保留证据诚实边界，不再为无法组织的外部样本冻结核心玩法迭代。
- **后果**：P6.7、HV-R1、HV-UI、HV-A11Y、HV-E2E、HV-FB 与 HV-MAINT 项全部退出强制门禁；相关方案可继续用于自愿研究。阶段出口仍必须通过自动测试、完整对局代理、确定性、公平知识、性能、UI 实渲、存档和产品负责人审查。
